# Storage

Local storage is the default in generated applications. The development `s3-storage` feature exposes a private S3-compatible backend; it is not in published Fexu 0.2.0. It does not automatically replace local upload routes or settings.

Enable `features = ["s3-storage"]` on a matching development source dependency on Fexu. Provision a private bucket and restrict credentials to its Fexu media prefix. Set `FEXU_S3_ACCESS_KEY` and `FEXU_S3_SECRET_KEY` in the environment.

```rust
use fexu::storage::{
    credentials_from_env, prepare_s3, S3Limits, S3Storage, Storage,
    ACCESS_KEY_ENV, SECRET_KEY_ENV,
};

let plan = prepare_s3(
    "https://storage.example",
    "us-east-1",
    "app-media",
    ACCESS_KEY_ENV,
    SECRET_KEY_ENV,
)?;
let storage = S3Storage::new(
    &plan,
    credentials_from_env(&plan)?,
    S3Limits::default(),
    &["text/plain", "image/png"],
    None,
)?;
let file = storage.save(owner_id, "notes.txt", b"hello").await?;
let (_metadata, bytes) = storage.read_for(owner_id, owner_id, file.id).await?;
```

The example assumes a verified owner ID from the application session. It uses path-style S3 addressing and a regional endpoint. Private CA PEM bytes may be supplied in the final constructor argument; certificate checking remains enabled. No redirect or implicit HTTP proxy is followed. Configure the Rustls provider before construction if your application requires a different one.

The backend stores one versioned envelope per immutable owner/file UUID, including metadata and a SHA-256 digest. Do not serve raw bucket objects: they contain metadata as well as file bytes. Application downloads must enforce verified ownership and safe response headers. Existing signed-download tokens are application tokens, not S3 presigned URLs. The local HTTP routes are not automatically remote-enabled.

The default file cap is 10 MiB, up to 100 MiB; each request has a bounded timeout. A failed write may have reached storage even if its reply was lost. Automatic retries are disabled. Staged expiry is honored for reads and retain, but expired objects require explicit cleanup. Do not deploy remote staging without a reconciliation policy. No distributed owner quota, automatic orphan scan, multipart support, IAM role refresh or live AWS acceptance is claimed. The initial TLS MinIO contracts passed in PR #271. Additional CI coverage checks explicit concurrent retain/delete operations and persistence across a restart of the same disposable MinIO container. A restart is not a backup/restore or failover guarantee. Automatic expiry cleanup, distributed quotas and production lifecycle acceptance remain separate work.

### Explicit expiry reconciliation

The development backend exposes `cleanup_unreferenced_expired(owner, id)` for an operator or application reconciliation service. Call it only after establishing that no database reference exists and preventing new references during reconciliation. It skips missing, retained and not-yet-expired objects. A conditional tombstone write fences a stale retain before physical deletion; a failed cleanup can be retried using the same immutable ID. There is no scheduled sweep, automatic account purge or database transaction. Do not write or recreate raw keys outside Fexu. Keep server clocks synchronized; bucket versioning may retain historical bytes and requires separate retention policy. The targeted cleanup contract passed in PR #273. Additional deterministic tests exercise a stale ETag after retain and resuming a cleanup from a persisted deletion marker; both tests passed in PR #274. They simulate interruption between requests, not a network fault or server crash.

### Reference-aware reconciliation

Use `reconcile_expired` with an application implementation of `ReferenceCheck` and the S3 backend. The check returns `Referenced`, `Unknown`, or `Unreferenced(guard)`. Only the last decision permits cleanup; lookup errors propagate. The guard must exclude new database references across every writer for the entire cleanup operation. This API keeps the guard alive across storage I/O but cannot prove that an application implements distributed exclusion correctly. No default database adapter, scheduled scan or automatic local cleanup is enabled. Existing local `cleanup_orphans` is not reference-aware; do not run it on live referenced media. The reference-aware contract passed in PR #275.

### Opt-in reference ledger

`ReferenceLedger` provides a durable admission/retirement gate shared by SQLite and PostgreSQL writers. Explicitly initialize its table with `initialize` during controlled setup, then enroll only newly allocated media IDs with `register`. Every model reference addition and removal must call `attach` or `detach` in the same database transaction as the model write. The ledger stores a count, not a discovery scan. Missing rows are unknown; retirement is irreversible and requires zero references. `ReferenceCheck` commits retirement before allowing storage cleanup, so a lost connection cannot reopen admission. A retired key remains retired even if storage cleanup fails or finds a permanent or future-dated file. Only submit expired candidates that will never be reused; keep the ledger and media backups consistent. Do not enroll existing media without a separately verified reference migration. Direct writers, legacy form deletion, automatic enumeration and production integration are not covered. The ledger runtime contracts passed on both databases in PR #277.

### Reference-aware model save

After validating and staging an upload, use `StagedMedia::commit_referenced(&storage, &db, save)` instead of the legacy `commit` or `finish_media` path. The async save closure receives the transaction, previous field bindings and replacement bindings. It must compare the current authorized model fields against the previous values under a row lock or an atomic conditional write, persist exactly the replacement values, and return an error on conflict. Do not start or commit a separate transaction. The coordinator enrolls and attaches new IDs, detaches replaced IDs, retains new bytes before committing, and never deletes old bytes. Detached IDs are candidates only, not deletion permission. On any failure, new candidate IDs are reported and no file is deleted; retained but unreferenced bytes can require manual recovery. Cancellation may leave staged or permanent orphans. Do not treat a commit error as proof of rollback. All writers must use the ledger; legacy forms/admin and automatic cleanup remain unintegrated. The SQLite and PostgreSQL model-row contract tests passed in PR #278.

### Explicit orphan discovery and cleanup

`ReferenceLedger::orphan_candidates(after, limit)` returns up to 1,000 enrolled zero-reference IDs in deterministic owner/file order. Pass the last ID as the next cursor, and restart from the beginning on later scans. Results are not a snapshot or permission to delete; newly registered or temporarily unreferenced files can be present. Retired IDs remain visible for repeatable recovery. `cleanup_abandoned(&storage, media)` is an explicit operator operation for permanently abandoned IDs only, including retained files. It commits the irreversible zero-reference retirement before calling the backend delete operation. Unknown and referenced IDs are skipped. Missing and removed bytes are distinguished according to the backend's delete result; errors leave the retirement intact. Do not run this on unexpired staged uploads, in-flight saves, legacy files, or storage shared with nonparticipating writers. No background worker, automatic eligibility policy, physical inventory, durable pre-upload registration, or recovery of unknown IDs is provided. The SQLite/PostgreSQL orphan contracts passed in PR #279.

### Reserved uploads

`ReferenceLedger::stage_reserved` generates a fresh server-side ID, commits its enrollment before calling `Storage::save_reserved`, and returns the stored metadata or an error containing the attempted ID. The low-level reserved write rejects collisions: local storage uses exclusive temporary creation and hard-link publication (requires filesystem hard-link support), and S3 uses conditional creation. Never reuse IDs even after deletion. Other storage implementations reject reserved writes by default. The caller must authorize the upload, exclude cleanup while writes are in flight (including uncertain remote completion), and coordinate retention and model attachment in one model transaction. The legacy `StagedMedia::commit_referenced` registers its own fresh IDs; use the dedicated reserved staging path below for pre-enrolled uploads. Failed writes remain discoverable as enrolled candidates when registration succeeded. No automatic cleanup, durable upload-state machine, crash-proof local metadata publication or distributed writer lease is provided. The reserved upload and collision runtime contracts passed in PR #280.

### Reserved model staging

Use `UploadPlan::stage_referenced(&storage, &ledger, now, ttl)` and then `ReservedStagedMedia::commit(&storage, save)`. The wrapper keeps the enrolling database connection and has no legacy abort/delete method. Use the same storage namespace for both operations. The transaction claims only enrolled zero-reference, non-retired IDs, runs the authorized compare-and-write model callback, detaches previous references and retains the new files before committing. A rollback leaves the pre-enrolled IDs discoverable. A retired ID cannot reach the model callback. Failed staging reports attempted IDs without deleting bytes. All writers must cooperate; callers must exclude cleanup during in-flight uploads and uncertain remote writes. Automatic eligibility and worker integration are not provided. SQLite/PostgreSQL model contracts passed in PR #281.

### Durable upload states

Explicit ledger initialization creates a separate upload-state table without rewriting legacy enrollment rows. Reserved uploads atomically enroll the ID and record `Uploading` before storage I/O. Only a successful validated storage response advances it to `Staged`. The reserved model transaction changes it to `Committed` together with the reference claim; rollback restores `Staged`. Generic attach rejects tracked IDs until committed. Reference-aware retirement refuses `Uploading` and `Staged` IDs, returning `Unknown` (no deletion permission). Candidate enumeration is discovery only and may include protected IDs. `upload_state` observes state without retirement. `abandon_upload` explicitly transitions a settled, permanently abandoned upload to `Abandoned`; never call it on an uncertain or still-running write. Errors and cancellation remain protected, including ambiguous storage responses. Retirement and cleanup remain separate operations; committed uploads can become unreferenced through normal detach. Legacy IDs have no state record and retain their previous contract; do not mix old and new binaries during rollout. No automatic timeout, lease, worker or proof of remote write completion is included. The durable upload state contracts passed in PR #282.

### Bounded abandoned-upload cleanup

`abandoned_candidates(after, limit)` selects only tracked, explicitly abandoned IDs with zero references. Uploading, staged, committed (even detached), and legacy IDs are excluded. `cleanup_abandoned_page(&storage, after, limit)` processes at most 1,000 candidates sequentially and returns a per-ID result, including errors without stopping the remaining page. Each deletion requires the existing durable retirement gate. Advance the cursor using the last result ID; periodically restart from the beginning to retry failures and discover new candidates. Missing results reflect backend semantics, not proof of physical erasure. Retired IDs without a receipt remain in discovery. Run only with authorized storage namespaces and cooperating writers. The SQLite/PostgreSQL page contracts passed in PR #283.

### Durable cleanup receipts

Explicit ledger initialization creates a separate receipt table. Abandoned-page cleanup records the backend result (`Removed` or `Missing`) only after retirement and the storage operation; `cleanup_receipt(media)` reads that result. Discovery excludes IDs with receipts. Errors do not record completion; a crash after deletion but before recording leaves the retired ID eligible for retry. Concurrent workers can repeat a delete, and the first recorded result wins. These receipts describe backend responses, not proof of physical erasure: partial local files, S3 tombstones, object versions and backups may require separate reconciliation. The direct `cleanup_abandoned` API retains its original semantics. No automatic abandonment, scheduler, remote write settlement proof or mixed-version rollout support is supplied. The extended page contracts passed in PR #284.

### Unresolved upload recovery

`unresolved_uploads(after, limit)` lists up to 1,000 tracked Uploading IDs in keyset order, including live writers. `inspect_unresolved(&storage, media)` is non-destructive and reports `Present` (validated readable staged metadata and payload digest), `Missing`, `Expired`, or `NotUploading`; backend errors propagate. Observations are not proof of remote write settlement. Only after an operator establishes that all original writes have settled may `recover_settled_upload` transition a readable upload from Uploading to Staged. It does not create a model reference or reconstruct a lost form plan. Missing, expired, corrupt or uncertain reads do not change state. Use the same authorized storage namespace, and explicitly abandon only after settlement and a decision not to use the file. No timeout-based abandonment, remote fencing, or automatic deletion is supplied. The extended SQLite/PostgreSQL upload contracts passed in PR #285.

### Original upload intent journal

Ledger initialization creates `_fexu_media_upload_intents` without rewriting existing enrollment rows. New reserved uploads atomically record their original byte length, SHA-256 digest, staging deadline and sanitized filename alongside the ID and Uploading state before any storage I/O. `upload_intent(media)` reads these expected values. The successful storage response must match the intent and identity before advancing to Staged. Explicit settled-write recovery additionally requires the readable object's verified metadata and payload digest to match the recorded original intent; self-consistent but different bytes are rejected. Older unresolved uploads without an intent remain protected and cannot use this recovery transition. Read-only inspection continues to describe observed storage, not certify intent or settlement. Operators must still establish that every original write has settled before recovery or abandonment. The journal does not store file bytes, reconstruct form plans, establish remote fencing or authorize deletion. Use one authorized storage namespace and do not mix ledger versions. Extended SQLite/PostgreSQL contracts passed in PR #286.

### Permanent S3 discard fencing

For an authorized operator who has decided to discard an unresolved upload, `ReferenceLedger::abandon_unresolved_s3(&storage, media)` (feature `s3-storage`) first commits an irreversible discard request in `_fexu_media_upload_fences`. `upload_fence_requested(media)` exposes that durable request; normal staging, recovery and ordinary abandonment refuse it. If remote I/O fails or is interrupted, the Uploading state stays protected, and the same operation can be retried. The S3 backend conditionally creates an `FXF1` marker at an absent immutable key or conditionally replaces a validated existing object or expiry marker using its observed ETag. Only confirmed marker publication permits transition to Abandoned. Late conditional-create uploads cannot replace that marker; ordinary reads, retain, delete and expiry reconciliation cannot remove it. Retry is idempotent, including after an ambiguous final database commit. The marker must remain for the lifetime of the namespace: disable lifecycle expiration of these keys, exclude raw writes/deletes and non-cooperating or older binaries, and use exactly the original authorized bucket. Do not race raw destructive APIs with ledger-managed writes. This requires a backend implementing atomic conditional create/update and consistent reads; TLS MinIO contracts exercise both absent and existing keys and ledger cleanup. The marker is not proof of erasure of object versions or backups, and is intentionally never physically removed by Fexu. Local storage still requires operator-established settlement. The fencing contracts passed in PR #287.

### Targeted local residue reconciliation

After establishing that all local writers have settled, an authorized operator can explicitly abandon an unresolved upload and call `ReferenceLedger::cleanup_local_residue(&local_storage, media)`. The operation accepts only tracked Abandoned IDs without an S3 fence request, checks durable retirement before filesystem I/O, and removes only the four exact UUID paths (payload, `.json`, `.partial`, `.json.tmp`). It preflights all paths and rejects links, directories or other unexpected file types before deleting any. It tolerates absent files and is retryable after partial removal. Existing backend receipts are not overwritten and do not prevent explicit reconciliation. No directory-wide scan, sidecar reconstruction, timeout-based abandonment or cross-process writer exclusion is provided. Use the original trusted root, exclude concurrent filesystem changes and raw storage operations, and do not infer physical erasure from unlinking paths. SQLite/PostgreSQL contracts cover residue after receipts, preflight rejection and protected uploads; CI verification is required.

### Local exclusive writer slots

Current LocalStorage writers acquire an exclusive `{id}.write-lock` file before publishing bytes and release it after all tracked write paths have settled. `ReferenceLedger::abandon_unresolved_local(&storage, media)` commits an irreversible local discard request before attempting to occupy that same slot with a permanent `FXL1` marker. `local_fence_requested(media)` reports the request. Pending requests block normal staging, recovery and ordinary abandonment; S3 and local requests cannot be exchanged. A busy, crashed or malformed slot is never stolen automatically. Retry after a cooperating writer releases its slot; after a crash, an authorized operator must establish writer settlement before using the offline recovery operation below. Do not unlink an empty slot. Never remove a permanent marker. A confirmed marker permits Abandoned and targeted residue reconciliation preserves the marker. Requires a trusted shared filesystem supporting atomic exclusive file creation, the original root, current cooperating binaries, and no raw mutation, owner purge or legacy cleanup concurrent with ledger-managed operations. This is not a distributed lease, power-loss durability guarantee, or automatic stale-lock recovery. SQLite/PostgreSQL contracts exercise independent local handles and simulated occupied slots; real multi-process deployment acceptance remains outstanding. CI verification required.

### Offline stale writer slot recovery

`ReferenceLedger::recover_settled_local_discard(&storage, media)` is an explicit maintenance operation, not an automatic timeout or lease. First request discard using `abandon_unresolved_local`; if a slot remains occupied, stop and settle every writer and competing recovery operator sharing the original trusted root before invoking recovery. The operation requires a durable local discard request and Uploading or Abandoned state, rejects S3 requests, and converts an empty regular slot in place to `FXL1` without unlinking it or exposing a new writer admission window. An absent slot is exclusively created; an existing complete marker is synchronized and preserved. Unexpected contents, links and directories fail closed. Only successful marker synchronization permits the Abandoned transition; the operation is retryable. A partially written marker requires separate offline investigation; no age, PID or timeout proves settlement. No physical erasure or power-loss guarantee is supplied. SQLite/PostgreSQL tests simulate stale slots and malformed markers; actual multi-process acceptance remains outstanding. CI verification required.

### Bounded cleanup worker batches

`ReferenceLedger::cleanup_abandoned_batch(&storage, after, page_size, max_pages)` is a bounded worker entry point for an explicitly configured scheduler. Use the original trusted storage namespace and the same ledger as all cooperating writers. It attempts at most 16 pages and 1,000 candidates, returning per-ID outcomes, a continuation cursor, an end-of-sweep flag and any page-query error. Persist or carry `next_after` between invocations; when `reached_end` is true, begin the next sweep at `None` so failed or newly eligible earlier IDs are revisited. A page-query failure leaves the cursor at the last completed page. Durable backend receipts suppress successfully completed IDs, including after a worker restart. Inspect individual outcomes and `scan_error` rather than treating a successful outer result as success of every item. No automatic abandonment, committed-ID cleanup, raw directory scan, local residue cleanup or scheduler registration is performed. A single configured worker is recommended; overlapping workers may repeat backend calls. The existing cleanup receipt is not proof of physical erasure. Extended SQLite/PostgreSQL contracts passed in PR #291.

### Persistent cleanup jobs

Register `fexu::jobs::StorageCleanupHandler::new(ledger, storage, page_size, max_pages)?` explicitly with the worker registry or WorkerHost. `storage` is an `Arc<dyn Storage>` bound to the original trusted namespace. The job payload is an empty object; it cannot select a path, bucket, owner, media ID or abandonment policy. Enqueue with `fexu::jobs::enqueue_storage_cleanup(&queue, When::every("storage-cleanup", 60)).await?` (or `When::now()` / `When::cron(...)`). Initialize the ledger and apply job migrations separately before starting the worker. No schedule or worker is enabled automatically. Each invocation attempts a bounded batch, records only counts in logs, and keeps a process-local cursor across invocations; restart from the beginning is safe because durable receipts exclude completed IDs. Scan or item errors report retryable job failures; after exhausting attempts the existing queue stops that schedule until an operator retries it. A successful partial batch schedules its next normal occurrence; it does not imply the sweep is complete. Configure one trusted worker per namespace; at-least-once redelivery may repeat backend calls. The 120-second handler timeout is not a hard bound on blocking local filesystem I/O. Local residue reconciliation and automatic abandonment are not part of this handler. SQLite/PostgreSQL recurring-job contracts passed in PR #292.

### Explicit cleanup admission for detached committed media

After authorizing permanent deletion and establishing that all external references and storage writes have settled, call `ReferenceLedger::admit_detached_cleanup(&tx, media)` in the same database transaction as removal of the final model reference (after `detach`), or in a fresh transaction after removal. The method atomically retires a tracked Committed ID with zero references and changes its upload state to Abandoned. It returns false for IDs that are not eligible, including already admitted, referenced, unknown, staged, uploading and legacy IDs. Roll back the entire transaction on error. After commit, attachment is permanently refused and the existing abandoned-only worker may process the ID, subject to the original trusted storage namespace and normal cleanup constraints. Rollback preserves attachment eligibility for an originally unretired ID. The method does not delete bytes, authorize users, automatically select all detached media, or implement retention/legal-hold policies. Existing detach behavior is unchanged. Applications must opt in only when permanent deletion is intended. SQLite/PostgreSQL contracts cover shared references, rollback, reattachment exclusion and subsequent cleanup; CI verification required.

### Per-save detached media policy

`ReservedStagedMedia::commit_with_policy(&storage, DetachedMediaPolicy::Cleanup, save)` opts into cleanup admission for detached tracked committed media inside the model transaction. The default `commit` and legacy referenced commits retain detached files. All detach operations run before admission so shared references remain protected. The application must authorize permanent deletion and establish that external references and original storage writes have settled. Ineligible or legacy IDs remain unadmitted. No physical deletion occurs in the model transaction; the configured persistent cleanup worker handles admitted IDs after commit. A rollback also rolls back admission. The existing report lists detached IDs, not proof of cleanup eligibility or deletion. SQLite/PostgreSQL model roundtrip contracts require CI verification.

### Distributed owner admission budgets

Before the first enrollment of a new owner, an authorized operator may call `ReferenceLedger::configure_owner_quota(owner, max_files, max_bytes).await?`. Zero is a real limit; an unconfigured owner uses the signed 64-bit maximum for both limits. All reserved uploads acquire the database owner row and charge one file and the original intent byte length in the same transaction as enrollment, before storage I/O. `owner_quota(owner)` returns the persisted limits and counters. Concurrent cooperating writers share the budget, and rejected admissions do not enroll IDs. Failed or ambiguous writes remain charged. The implementation is deliberately conservative: no cleanup receipt, timeout or abandonment automatically releases budget. Counters are logical reservations since deployment of this schema, not physical disk usage; old enrollments, raw storage and legacy saves are outside this accounting. Existing owners cannot be configured without a separate reconciliation procedure; use a fresh owner in a namespace where every writer uses reserved admission. Do not mix older binaries or raw writers. Initialize the ledger explicitly before rollout. SQLite/PostgreSQL runtime contracts require CI verification.

### Explicit settled quota release

New reserved admissions journal the exact per-ID charge in the enrollment transaction. After an authorized operator has established permanent abandonment, settlement of every writer, and removal of relevant storage residue in the original trusted namespace, `ReferenceLedger::release_settled_quota(media).await?` may return capacity. A durable cleanup receipt, retired zero-reference state, Abandoned upload state and an unreleased per-ID charge are required. A receipt alone is not evidence of physical absence: for local storage reconcile the known residue paths separately, and for S3 consider permanent markers, versioning and external lifecycle rules. The release changes the charge and owner counters atomically under the owner lock; repeat calls return false. Older reservations lacking a per-ID journal remain charged, including reservations made with the initial quota implementation in #295. No historical backfill is inferred. The caller must not release capacity while any writer can still publish bytes. No automatic release or physical deletion occurs in this explicit API. The SQLite/PostgreSQL contracts passed in PR #296.

### Local fenced quota cleanup

For an explicitly abandoned ID, `ReferenceLedger::cleanup_and_release_local_quota(&storage, media).await?` combines permanent local writer fencing, retirement, reconciliation of the four managed residue paths, durable receipt recording and once-only quota release. Use only the original authorized local root with current cooperating writers; exclude raw mutation, owner purge and legacy cleanup. An empty or malformed writer slot fails closed and is never stolen. Existing receipts do not bypass physical reconciliation. A permanent `FXL1` marker remains; logical quota does not account for marker overhead or backups. Live, unknown and S3-fenced IDs are ineligible. Unjournaled charges stay reserved. Retry after a cleanup or database failure; only a newly released charge returns true. This is an opt-in per-ID operation, not automatic abandonment, namespace discovery or scheduled sweeping. Remote release, historical reconciliation and real multi-process acceptance remain open. SQLite/PostgreSQL contracts passed in PR #297.

### Scheduled local quota cleanup

For a ledger dedicated exclusively to one original trusted local root, explicitly register `fexu::jobs::LocalQuotaCleanupHandler::new(ledger, storage, page_size, max_pages)?` with an `Arc<LocalStorage>` and enqueue `fexu::jobs::enqueue_local_quota_cleanup(&queue, When::every("local-quota-cleanup", 60)).await?`. Never use a mixed-root or mixed-backend ledger: the schema does not record a namespace per charge. The empty job payload cannot select storage or IDs. The underlying `cleanup_local_quota_batch` attempts at most 16 pages and 1,000 journaled, unreleased, abandoned zero-reference IDs, excluding S3-fenced IDs. Unlike ordinary cleanup, existing receipts do not exclude candidates. A restart begins from the start; released journals are excluded, and failures remain eligible on a later sweep. The worker reports counts and retryable errors, and keeps a process-local continuation cursor. No schedule is enabled by default. Use current cooperating writers and exclude raw mutation, owner purge and legacy cleanup. No automatic abandonment, remote release, historical backfill or production crash acceptance is supplied. Shared SQLite/PostgreSQL job contracts passed in PR #298.

### Explicit S3 fenced quota release

With `s3-storage`, an authorized operator may call `ReferenceLedger::release_fenced_s3_quota(&storage, media).await?` after the existing permanent S3 discard protocol has completed. Verify the original bucket, settlement of all destructive operations, and removal or absence of relevant historical object versions before calling. The method requires Abandoned state, a durable S3 discard request, zero references and permanent retirement; it rejects local fence requests. It reads and verifies the exact current `FXF1` marker even when a cleanup receipt already exists, records a receipt if needed and releases the journaled logical charge once. Missing or unexpected markers fail closed; no marker is recreated by this method. Preserve the marker for the namespace lifetime. No raw mutation, concurrent deletion, lifecycle expiration of markers or mixed-version writers are permitted. This API does not enumerate or remove historical versions, verify bucket versioning settings or erase backups. Marker overhead is outside logical quota accounting. Ordinary abandoned S3 IDs without a durable S3 fence, automatic remote scheduling, historical reconciliation and production acceptance remain open. TLS MinIO contract passed in PR #299.

### Permanent fencing of abandoned S3 media

An authorized operator can call `ReferenceLedger::fence_abandoned_s3(&storage, media).await?` for a tracked, explicitly abandoned S3 ID with zero references, including media previously admitted through detached-media cleanup. Use the original trusted bucket and settle all destructive operations, including ordinary delete and expiry cleanup, before fencing. Do not overlap those operations with fencing. The ledger retires the ID and durably records the S3 discard request before conditional marker publication. Unknown, protected and locally fenced IDs are ineligible. Existing cleanup receipts do not bypass fencing; absent keys receive the permanent marker and validated present objects are conditionally replaced. Failed remote operations leave a retryable request. A confirmed marker records a backend receipt and returns true, including on retry. The method does not release quota. Separately verify historical object versions and invoke `release_fenced_s3_quota` under its existing operator contract. Preserve markers permanently; no automatic S3 sweep or version-history verification is supplied. TLS MinIO contract verification is pending CI.
